# Fluxo canônico de status do quote e regra de abatimento da verba

## A ordem é uma SEQUÊNCIA, não um set de flags

Cotações têm um ciclo de vida. Cada status é um ponto nessa sequência, e **a posição importa**: o que vem depois de "approved" (incluindo o próprio approved) **abate a verba**. Não é só `approved`, é **approved + tudo depois**.

## Ordem canônica (QUOTE_FLOW)

Definida em `.fractal/artifacts/dashboard/source/src/utils/budget.js`:

```
draft      → 0  Rascunho interno
pending    → 1  Em cotação com o fornecedor
quoted     → 2  Cotação recebida do fornecedor
sent       → 3  Enviada para aprovação (cliente/Ademar)
approved   → 4  ★ PRIMEIRA FASE QUE ABATE A VERBA
ordered    → 5  Pedido feito ao fornecedor (continua abatendo)
invoiced   → 6  NF emitida (futuro)
delivered  → 7  Entregue (futuro)
checked    → 8  Conferido (futuro)
done       → 9  Concluído (futuro)
rejected   → saída — não abate
```

## Helpers exportados pelo `utils/budget.js`

- `QUOTE_FLOW` — array canônico na ordem
- `QUOTE_STATUS_LABEL` — labels em PT-BR
- `isApprovedOrAfter(status)` — true se status está em approved ou depois (exceto rejected)
- `flowIndex(status)` — posição no array, -1 se desconhecido

## Regra de negócio

> **Consumido da verba = soma de `quote.total` onde `isApprovedOrAfter(quote.status) === true`**

Quando uma cotação é marcada como "approved", o valor sai da verba. Se ela avançar para "ordered" (pedido feito), "invoiced" (NF), "delivered" (entregue), etc., o valor **continua abatido** — o compromisso com o fornecedor já foi assumido.

## Padrão a seguir para lugares futuros

Quando criar uma nova tela que mostra status de quote:
1. Importar `QUOTE_FLOW` e/ou `QUOTE_STATUS_LABEL` de `utils/budget`
2. Para verificar se abate verba: `isApprovedOrAfter(quote.status)`
3. Para ordenação de chips/filtros: gerar a partir de `QUOTE_FLOW`
4. Para total "consumido": `quotes.filter(q => isApprovedOrAfter(q.status)).reduce((s, q) => s + (q.total || 0), 0)`

## Lições

- A ordem anterior nos Kanbans era `draft → pending → quoted → approved → sent` — mas `sent` vem **antes** de `approved` no fluxo. Isso mostra que o código foi escrito em uma fase em que o fluxo não estava documentado, e cada tela acabou inventando sua própria ordem.
- Sempre que criar um array de status, derivar de `QUOTE_FLOW` em vez de hardcodar — evita esse tipo de drift.
- A função `isApprovedOrAfter()` existe **justamente** pra evitar ter que lembrar "approved + ordered + invoiced + delivered + checked + done" em cada call site. Se você ver `q.status === "approved" || q.status === "ordered" || ...` no código, é candidato a refatorar.
