# Lição: Simplificar Schema ao Invés de Complexificar

## Contexto (2026-05-21)
O usuário (Felipe) tinha duas collections: `requests` e `quotes`. Ele pediu para simplificar porque:
- Não queria lógicas complexas para múltiplas cotações por pedido
- Queria focar em um fluxo simples: um pedido = uma cotação = um registro

## Decisão
1. **Deletamos** a collection `requests`
2. **Unificamos** tudo em `quotes`
3. **Normalizamos** com referências por ID:
   - `project` → ID da collection `projects`
   - `supplier` → ID da collection `suppliers`
4. **Adicionamos** campo `file` para linkar o Excel do pedido

## O que aprendi
- **Sempre perguntar** se o usuário quer complexidade ou simplicidade
- **Preferir normalização** com IDs em vez de duplicar dados
- **Um registro, uma verdade** — evitar múltiplas collections quando uma resolve
- **Status tracking** é suficiente (`quoted` → `sent` → `approved` → `ordered`)

## Quando complexificar no futuro?
- Quando precisar de **múltiplas cotações** para o mesmo pedido (comparar fornecedores)
- Quando precisar de **histórico de versões** de cotações
- Quando o **volume de dados** justificar separação

## Aplicação
Válida para qualquer schema no Fractal. Começar simples, evoluir conforme necessidade real.
